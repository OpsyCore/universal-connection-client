# VPN / TUN engine

## Components

| Class | Responsibility |
|---|---|
| `UcVpnService` | Foreground `VpnService`. Translates `TunRequest` → `VpnService.Builder`, holds the `ParcelFileDescriptor`, posts the status notification, reports `onRevoke`. |
| `AndroidTunnelHost` | Verifies `VpnService.prepare()==null`, starts the service, waits for the instance (10 s), exposes it as `TunProvider`. |
| `AndroidNetworkMonitor` | `registerBestMatchingNetworkCallback` for `INTERNET & NOT_VPN` — always the *underlying* network. Emits `DefaultChanged(key, transport)` / `Lost`; feeds interface name/index to the core. |
| `AndroidPlatformInterface` | libbox `PlatformInterface`: `openTun`, `autoDetectInterfaceControl` (→ `protect(fd)`), interface enumeration, connection-owner lookup (API 29+), system CA export, local DNS transport. |
| `LocalDnsTransport` | sing-box `local` DNS server → `android.net.DnsResolver` bound to the underlying `Network` (raw queries on API 29+). |

## TUN parameters (Phase 1 defaults)

Generated by `SingBoxConfigGenerator.tunInbound`:

- `172.19.0.1/30` (+ `fdfe:dcba:9876::1/126` when IPv6 enabled)
- `auto_route: true`, `strict_route: true` (configurable via `CoreStartOptions`)
- `stack: mixed` (system TCP + gVisor UDP)
- MTU 9000 default (sing-box recommendation for gVisor; configurable)
- `include_package` / `exclude_package` passed straight through to
  `Builder.addAllowedApplication` / `addDisallowedApplication` (Phase 6 UI)

sing-box computes routes; on API 33+ we use `addRoute(IpPrefix)` +
`excludeRoute`, below that the pre-computed route ranges from the core.

## Feature status (honest)

| Requirement | Status |
|---|---|
| TUN, IPv4, IPv6, TCP, UDP | Implemented via sing-box TUN inbound; **device verification pending** (no emulator in the build sandbox) |
| DNS handling | `hijack-dns` route action + typed DNS servers; proxy hostname resolved via `local` (underlying network) |
| Route configuration | auto_route + strict_route; custom rules land in Phase 6 |
| Kill switch | **Not implemented yet.** Plan: `strict_route` already blocks leaks while the TUN exists; the "block when disconnected" mode requires Android's always-on + lockdown (system setting we can only deep-link to) — will be documented, not faked. |
| Always-on | `SUPPORTS_ALWAYS_ON` meta-data declared; null-intent restart path re-connects the last profile |
| Background operation | Foreground service with `specialUse` type + notification |
| Reconnect / network change | `DefaultConnectionManager` reconnect loop, deterministic backoff (1 s·2ⁿ, cap 15 s, 5 attempts) |
| Process recreation | `START_STICKY` + `LastProfileStore` |
| User disconnect | Notification action → `ACTION_STOP` → `manager.disconnect()` |

## sing-box pin & upgrade checklist

Pinned: `v1.13.21` (`core/engine-singbox/singbox.version`). To upgrade:

1. Bump the version file; CI rebuilds `libbox.aar` (cache key changes).
2. Diff `experimental/libbox/platform.go` `PlatformInterface` between tags and
   update `AndroidPlatformInterface` (1.14 adds shell/bridge/SSH/Tailscale hooks).
3. Diff `TunOptions` (1.14 changes `GetDNSServerAddress` to an iterator + `GetDNSMode`).
4. Run `SingBoxConfigGeneratorTest`; check `Libbox.checkConfig` in an instrumentation test.
5. Pin the new AAR SHA-256 in `core/engine-singbox/libbox.sha256`.


## Reconnection model — why there is no "make-before-break" (v1.0.4 note)

Network changes (Wi-Fi ↔ mobile, default network restored) do **not** tear the tunnel down: `DefaultConnectionManager.reconnectLoop(restartCore = false)` keeps the `VpnService` and the TUN file descriptor as they are and only calls `CoreAdapter.onNetworkChanged()` (libbox re-binds its outbound sockets to the new default network) followed by a probe. Apps keep their TUN routes throughout; the only user-visible gap is the upstream handshake, which no client can avoid. The core is restarted (`restartCore = true`) solely after a *fatal core error*, and even then the existing TUN is reused (`tun ?: tunnelHost.acquire(profile)`), so the interface is not re-established and Android shows no VPN-off moment.

A literal make-before-break (second core + second TUN running in parallel, then swap) is not implemented and is not planned: Android allows one `VpnService` interface per app (`establish()` replaces the previous fd), libbox is a single instance per process, and the swap would double memory and open a real leak window while both are alive. The current model is the zero-gap variant that is actually achievable on Android; it is device-verified and part of the locked networking layer.
